1.1 CONFIGURATION CONTEXT STRUCTURES
------------------------------------

ngx_stream_conf_ctx_t:

------------------------------

2. Creates ngx_stream_conf_ctx_t with main_conf and srv_conf arrays
3. Calls preconfiguration() on all modules
4. Parses stream block content (server{} blocks, directives)
5. Calls init_main_conf() and merge_srv_conf() for each module
6. Calls postconfiguration() for handler registration
7. ngx_stream_variables_init_vars() - initializes variables
8. ngx_stream_init_phase_handlers() - compiles phase handlers into engine
9. ngx_stream_optimize_servers() - builds listening sockets

==============================================================================
3. PHASE EXECUTION MODEL
==============================================================================

3.1 PHASE HANDLERS AND CHECKERS
-------------------------------

Phase Handler Checkers (special phase logic):
  - ngx_stream_core_generic_phase: used by most phases
    Returns: NGX_OK (stop phase loop)
             NGX_AGAIN (continue to next handler)
             NGX_DECLINED (try next handler)
             NGX_ERROR, NGX_AGAIN, NGX_DONE (finalize)

  - ngx_stream_core_preread_phase: special handling for preread
    Manages buffer creation, timeout, event handling
    May return NGX_AGAIN (async read pending)

  - ngx_stream_core_content_phase: special handling for content
    Calls content_handler_pt which returns void

3.2 SESSION HANDLER FLOW
-----------------------

ngx_stream_init_connection(ngx_connection_t *c):
  1. Find server config for address:port
  2. Create ngx_stream_session_t
  3. Initialize session context arrays
  4. Set phase_handler = 0
  5. Call ngx_stream_core_run_phases(s)

ngx_stream_core_run_phases(ngx_stream_session_t *s):
  Loop through phases:
    1. Get current phase_handler index
    2. Get phase_engine.handlers[index]
    3. Call phase checker function
    4. If rc == NGX_OK, stop and return
    5. Otherwise continue

Phase execution continues via event callbacks:
  - ngx_stream_session_handler(ngx_event_t *rev)
    Called on read/write events
    Calls ngx_stream_core_run_phases() again

3.3 PHASE ORDER AND PURPOSE
--------------------------

1. POST_ACCEPT: After TCP connection accepted
   - For protocol detection, real_ip extraction
   - Early request analysis

2. PREACCESS: Before access checks
   - Geo-location checks, variable computation
   - Request classification

3. ACCESS: Access control
   - Access rules, limit_conn

4. SSL: SSL/TLS handling
   - SSL handshake, certificate selection
   - SNI processing

5. PREREAD: Read initial client data
   - Buffer initial bytes before deciding handler
   - Protocol detection (SSL, HTTP detection for proxy)
   - May wait asynchronously for data

6. CONTENT: Main content handler
   - Route decision (which upstream)
   - Proxy handling (bidirectional copy)
   - Response generation

7. LOG: Session logging
   - Write session stats to log files
   - Called on session close

Note: Unlike HTTP, stream has NO rewrite phases, NO location matching.
Server is selected at listen time (address:port) and optionally by
server_name matching.

4.1 SIMILARITIES
---------------

HTTP (lib.rs constants):
  - NGX_HTTP_MAIN_CONF (0x02000000)
  - NGX_HTTP_SRV_CONF (0x04000000)
  - NGX_HTTP_LOC_CONF (0x08000000) [Stream has UPS_CONF]
  - NGX_HTTP_UPS_CONF (0x10000000)

HTTP Phases:
  0. POST_READ_PHASE
  1. SERVER_REWRITE_PHASE
  2. FIND_CONFIG_PHASE
  3. REWRITE_PHASE
  4. POST_REWRITE_PHASE
  5. PREACCESS_PHASE
  6. ACCESS_PHASE
  7. POST_ACCESS_PHASE
  8. PRECONTENT_PHASE
  9. CONTENT_PHASE
  10. LOG_PHASE
  Total: 11 phases

HTTP Core Structures (core.rs):
  - CoreMainConf: servers, phase_engine, headers_in_hash
  - PhaseEngine: handlers, server_rewrite_index, location_rewrite_index
  - Phase: handlers (Vec<HandlerFn>)
  - PhaseHandler: checker, handler, next
  - Checker enum: Generic, Rewrite, FindConfig, PostRewrite, Access, PostAccess, Content

HTTP Handler Pattern:
  HandlerFn = Rc<dyn Fn(R) -> BoxFut<i64>>  (async closure)
  Returns i64 status code

HTTP Core_rt Pattern (core_rt.rs):
  - async fn handler(r: R) -> i64
  - async fn run_phases(r: R) -> i64
  - PhaseStep enum: Continue, Finalize(i64)
  - Each checker is an async function
  - Matches on checker type, awaits handler

4.2 KEY DIFFERENCES
-------------------

Stream vs HTTP:

Model:
  HTTP: Multiple requests per connection, request/response model
  Stream: Single bidirectional session per connection

Configuration:
  HTTP: 3-level nesting (main/server/location), location tree
  Stream: 2-level nesting (main/server), address:port selection + optional server_name

Phases:
  HTTP: 11 phases including rewrite, location matching,
        PostAccess guard before content
  Stream: 7 phases, no rewrite/location, simpler flow

Variables:
  HTTP: Per-request context, function pointers for get/set
  Stream: Per-session context, simpler variable handling

Headers:
  HTTP: Complex header parsing, filtering, merging
  Stream: No headers at core level, bidirectional byte streams

Content Generation:
  HTTP: Responses must be generated, headers required
  Stream: Content handler manages bidirectional copy/proxy

Async Model:
  HTTP: Rust-based with tokio async/await
  Stream: C-based with event loop, needs async Rust translation

4.3 ASYNC TRANSLATION NOTES
---------------------------

In C, phases are synchronous with callback-based async:
  - Phase handler returns NGX_AGAIN to suspend
  - Event callback re-enters handler later
  - Multiple entries into same handler with state tracking

In Rust async pattern (based on HTTP):
  - HandlerFn is async closure
  - Returns futures
  - Checker logic becomes async
  - No re-entry complexity

For Stream preread:
  C version:
    1. First call: start read, setup timer, return NGX_AGAIN
    2. Event fires: re-enter same handler with more data
    3. Handler decides if enough data or return NGX_AGAIN again
    4. Eventually: return NGX_OK or NGX_DECLINED

  Rust async version:
    1. async fn that awaits on socket read
    2. Returns when enough data present
    3. No multiple re-entries, natural async flow

7.2 PHASE ENGINE COMPILATION
-----------------------------

Key algorithm (in ngx_stream_init_phase_handlers):
  1. Collect all handlers registered in each phase
  2. Create array of phase_handler_t
  3. For each phase (except LOG):
     - Iterate handlers in REVERSE order (stack-like)
     - Set checker based on phase type
     - Link next pointer to continue chain
  4. Add content phase handler
  5. Handlers array forms execution chain

Checkers needed:
  - generic_phase: standard handler
  - preread_phase: special buffer/timeout handling
  - content_phase: content handler wrapper

7.3 RUNTIME SESSION HANDLING
----------------------------

Entry point: ngx_stream_init_connection(ngx_connection_t *c)
  1. Determine server config by address:port
  2. Allocate ngx_stream_session_t
  3. Copy main_conf, srv_conf pointers
  4. Call ngx_stream_core_run_phases()

Session loop: ngx_stream_core_run_phases(ngx_stream_session_t *s)
  Loop:
    1. Get phase_handler index
    2. Get handlers[index]
    3. Call checker function
    4. Checker returns status:
       - NGX_OK: stop loop (phase complete or error finalized)
       - NGX_AGAIN: continue loop
    5. If handler suspends (NGX_AGAIN returned), break loop
       and wait for event callback

Event handling:
  - ngx_stream_session_handler(ngx_event_t *rev)
  - Re-enters core_run_phases() for same session
  - Phase index preserved in session->phase_handler

7.4 VARIABLE SYSTEM
-------------------

Variables hash:
  - Built from variable definitions during init_main_conf
  - Maps variable name to ngx_stream_variable_t
  - Supports exact and prefix matching

Variable value storage:
  - session->variables array (one per variable)
  - Lazy evaluation: computed on first access
  - Cached unless NGX_STREAM_VAR_NOCACHEABLE set

Variable types:
  - Static: computed once from connection/config
  - Dynamic: recomputed each access (e.g. time)
  - Indexed: compiled to index for fast lookup
  - Prefix: partial name match (e.g. proxy_protocol_tlv_*)

8. SESSION LIFECYCLE AND STATE TRANSITIONS
==============================================================================

Session Lifetime (Rust async perspective):

Creation:
  ngx_stream_init_connection()
    -> Allocate session
    -> Initialize fields
    -> Call run_phases() [async]

Phase Loop (async):
  run_phases(session)
    Loop:
      phase_handler_index = session.phase_handler
      ph = handlers[index]

      result = call checker(session, ph) [await if async]

      if result == NGX_OK:
        break (phase complete or error)
      else if result == NGX_AGAIN:
        continue (try next handler)
      else:
        (shouldn't happen)

Async Suspension:
  When handler returns NGX_AGAIN (read would block):
    - Return from run_phases()
    - Setup event for socket read
    - Session preserved in connection.data
    - Event fires on socket ready
    - Re-enter run_phases() for same session
    - Phase_handler index preserved

Content Phase Execution:
  Content handler (e.g. proxy_pass):
    - Initiates upstream connection
    - Sets up bidirectional copy
    - Returns void
    - Subsequent data copied by buffer filters

Session Cleanup:
  ngx_stream_finalize_session():
    - Record status/statistics
    - Close upstream (if any)
    - Schedule log phase
    - Trigger LOG phase handlers
    - Close client connection

Error Handling:
  NGX_STREAM_INTERNAL_SERVER_ERROR (500):
    - Finalize immediately
    - Close both directions
    - Log error

9. CONFIGURATION INITIALIZATION ORDER
==============================================================================

During Parse (stream block):

1. ngx_stream_block() called
   Create conf_ctx with arrays for main/srv configs

2. For each module:
   Call preconfiguration()
   - Register variables
   - Setup module hooks

3. Parse directives:
   - server blocks create srv_conf
   - listen directives call add_listen()
   - Other directives fill config structs

4. For each module:
   Call init_main_conf() [once per stream block]
   Call merge_srv_conf() [for each server block]
   - Inherit/override parent settings
   - Validate configuration
   - Setup hashes

5. ngx_stream_variables_init_vars()
   - Build variables hash

10. KEY PATTERNS FOR RUST IMPLEMENTATION
==============================================================================

Based on HTTP module pattern analysis:

1. Module Definition:
   Use module_index macro like HTTP:
     http_module_index!("ngx_http_core_module")
   For Stream:
     stream_module_index!("ngx_stream_core_module")

2. Configuration Structs:
   Use RefCell<T> for interior mutability during config phase
   See: CoreMainConf, CoreSrvConf in http/core.rs

3. Phase Handlers:
   type HandlerFn = Rc<dyn Fn(S) -> BoxFut<i64>>
   Where S is Stream session handle
   Return i64 status code

4. Phase Checking:
   enum Checker { Generic, Preread, Content, ... }
   async fn run_phases(s: S) -> i64
   Match on checker type, call handler

5. Variable System:
   Lazy evaluation with caching
   Variables stored in session array
   Access via variable index

6. Server Selection:
   Listen address/port determines server config
   Optional server_name matching
   Hash table for fast lookup

7. Connection Initialization:
   Entry from ngx_core accept handler
   Allocate session
   Spawn run_phases() task

8. Async Model:
   All phase handlers are async
   Suspension via await on socket operations
   Event loop resumes on socket ready
